# angle-lab — exhaustive audit, 2026-09-13

Scope: everything built so far (F0–F4 — core math, canvas, points), audited against Daniel's
16-point checklist. Goal was to actively find bugs, not confirm the app "works." Three sequential
passes (not parallel, to avoid file conflicts between agents): core math edge cases, coordinate/EXIF/
resize/stress fidelity, and touch/hit-test/magnifier/the real espagat use case. Every pass was spot-
verified independently (re-run tests, re-derived key numbers by hand, reproduced bugs before and after
the fix) before being accepted — no report was taken at face value.

**Result: 2 real bugs found and fixed, both in gesture handling. Zero bugs in the math core. 204/204
tests passing throughout.**

## Bugs found and fixed

1. **A second finger touching down in POINT mode left a stray point behind.** Point creation happens
   on the *first* finger's `pointerdown`, before the code can know a second finger is about to arrive
   and turn the gesture into a pinch. Fixed in `src/ui/app.js`: the point created this way is undone
   if the claim is cancelled by a second finger rather than released normally — using a signal
   (`event.type === 'pointerdown'` on the cancelling call) that `src/ui/pointerGestures.js` was already
   passing but nothing was reading.
2. **A duplicate `pointerdown` for an already-active pointer double-created a point from one touch.**
   Plausible on real hardware — the same class of odd event ordering that already motivated wrapping
   `setPointerCapture` in try/catch. Fixed with a one-line re-entrance guard in `pointerGestures.js`.

Both reproduced before the fix (stray point present / duplicate point present) and confirmed absent
after, independently of the auditing agent's own report.

## The espagat scenario specifically

Built a real EXIF-bearing JPEG (orientation 6, 4032×3024 sensor → 3024×4032 displayed, iPhone-realistic
dimensions), decoded through the real `loadBlob` path. Three landmark points placed by direct model
call at coordinates constructed so the true hip angle is exactly 170° by construction. Measured:
**170°, exact, 0 error.**

**What this does and doesn't prove**, stated plainly so it isn't overclaimed:

- **(a) Mathematical accuracy of the angle computation** — what the app guarantees. Confirmed to
  floating-point precision, here and across 204 core tests.
- **(b) Precision of where you tap a landmark** — what the app makes easy but can't guarantee. The
  touch radius and magnifier exist to help you land on the exact pixel you mean, at any zoom. If you
  tap 3 pixels off from the true landmark, the app faithfully measures the point you placed, not the
  one you intended — closing that gap is on the user (zoom in, use the magnifier), not the software.
- **(c) Biomechanical validity of landmark choice** — entirely outside the app's scope. Whether a given
  three-point choice is the right one for a "hip angle," and what a given reading means for training,
  is a coaching judgment the app has no opinion on.

## Documented, not fixed (real limitations, not bugs)

- iOS Safari's actual canvas-area ceiling is unverified — no failure observed up to 192MP on desktop
  Chromium, but the spec already flagged this as needing on-device confirmation.
- Real iPhone→iPad transfer specifics (iCloud sync, HEIC handling, color profiles) are outside what a
  single-browser-process test can prove.
- Pinch-zoom, Apple Pencil suppression, and the magnifier under an actual finger still need a physical
  device pass — everything here was verified via scripted Pointer Events exercising the real code
  paths, which is strong evidence for the logic but not a substitute for touching a real screen.
